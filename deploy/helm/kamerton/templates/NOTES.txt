Kamerton is installed in namespace {{ .Release.Namespace }}.

1. Open the UI:
     kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "kamerton.fullname" . }} {{ .Values.service.port }}
     open http://localhost:{{ .Values.service.port }}
{{- if include "kamerton.authSecretName" . }}
   Login is on: user name and password come from Secret {{ .Release.Namespace }}/{{ include "kamerton.authSecretName" . }}.
   Serve the UI over HTTPS (ingress with TLS) before exposing it beyond port-forward.
{{- else }}
   Login is OFF: anyone who can reach the UI can change systems, channels and
   tokens. Turn it on before exposing the UI:
     kubectl -n {{ .Release.Namespace }} create secret generic kamerton-auth \
       --from-literal=username=admin --from-literal=password='<strong password>'
     helm upgrade {{ .Release.Name }} <chart> -n {{ .Release.Namespace }} --reuse-values --set auth.existingSecret=kamerton-auth
{{- end }}

2. Describe a system: "Add system" in the UI, or apply a description:
     kubectl -n {{ .Release.Namespace }} apply -f https://raw.githubusercontent.com/kamerton-labs/examples/main/otel-demo/system.yaml
     kubectl -n {{ .Release.Namespace }} get systemdescriptions
   Descriptions that send notifications must live in this namespace (the
   AlertmanagerConfig can only reference Secrets in its own namespace).

3. Notification channels: open "Channels" in the UI.
{{- if .Values.telegram.uiSetup }}
   Telegram: paste a bot token from @BotFather; it is stored in Secret
   {{ .Release.Namespace }}/{{ .Values.telegram.secretName }}. Add the bot to your groups and choose the routing.
{{- end }}
{{- if .Values.email.uiSetup }}
   Email: enter the SMTP server and password; the password is stored in Secret
   {{ .Release.Namespace }}/{{ .Values.email.secretName }}.
{{- end }}
{{- if not .Values.externalURL }}
   externalURL is empty, so notifications contain no links. Set it to the URL
   people use to open the UI, e.g. --set externalURL=http://localhost:{{ .Values.service.port }}
{{- else }}
   Links in notifications point to {{ .Values.externalURL }}.
{{- end }}

4. Existing Prometheus / Alertmanager / Grafana: "Kamerton status" in the UI
   shows the programs Kamerton uses; addresses can be changed and checked there
{{- if .Values.stacks.discovery.enabled }}, and
   "Find installed" lists programs already running in the cluster
{{- end }}.
{{- if .Values.autoInstrument.enabled }}

eBPF auto-instrumentation is ON: DaemonSet kamerton-auto-instrument runs on every
node {{ if (index .Values "opentelemetry-ebpf-instrumentation").privileged }}as a privileged container{{ else }}with SYS_ADMIN and other added capabilities{{ end }} with hostPID (see SECURITY.md) and records
HTTP/gRPC calls of pods in {{ with .Values.autoInstrument.namespaces.include }}{{ join ", " . }}{{ else }}all namespaces{{ end }} except {{ .Release.Namespace }}{{ range .Values.autoInstrument.namespaces.exclude }}, {{ . }}{{ end }}.
Restart workloads that were already running so gRPC method names are read from
new connections, and restart the DaemonSet after changing autoInstrument values:
     kubectl -n {{ .Release.Namespace }} rollout restart daemonset/kamerton-auto-instrument
{{- end }}
{{- if .Values.grafana.enabled }}

5. Grafana admin password (generated by the Grafana chart):
     kubectl -n {{ .Release.Namespace }} get secret kamerton-grafana -o jsonpath='{.data.admin-password}' | base64 -d
{{- end }}
